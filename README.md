# Avand — gold wallet and trading demo

وب آزمایشی فارسی برای خرید و فروش طلا. تمام قیمت‌ها، پرداخت‌ها و تسویه‌ها ساختگی‌اند.

## اجرا

Docker Desktop را اجرا کنید، سپس:

```sh
docker compose up --build -d
```

وب: http://localhost:3000 — RabbitMQ management: http://localhost:15678 (local demo credentials: `avand` / `avand_local`). سرویس‌ها فقط روی loopback میزبان منتشر می‌شوند. دیتابیس volume پایدار دارد؛ restart موجودی را پاک نمی‌کند.

برای توسعه با Node.js 22:

```sh
npm ci
docker compose up -d db rabbit
npm run migrate
npm start
# در ترمینال دیگر:
npm run worker
```

برای اجرای host از `HOST=127.0.0.1 npm start` استفاده کنید اگر فقط دسترسی محلی می‌خواهید. Docker API داخل container روی 0.0.0.0 است ولی port میزبان روی 127.0.0.1 bind شده است.

## تست

تست‌ها روی دیتابیس جداگانه اجرا می‌شوند و دادهٔ دمو را پاک نمی‌کنند. تنها بار اول:

```sh
docker compose exec db createdb -U avand avand_test
```

سپس:

```sh
npm run typecheck
npm test
```

`TEST_DATABASE_URL` اختیاری است و باید به دیتابیس با نام `avand_test` اشاره کند. هفت سناریوی مالی از PostgreSQL واقعی استفاده می‌کنند؛ تست worker نیز RabbitMQ واقعی می‌خواهد. تست worker صف جدا دارد.

## نمایش دمو

۱. در فرم «شارژ کیف پول»، مبلغ را ثبت و سپس در پنل درگاه «پرداخت موفق» بزنید. شارژ بدون کارمزد و بدون خرید طلا انجام می‌شود.
۲. «دریافت قیمت تازه» را بزنید؛ قیمت ماک داخل بازار هر ۳۰ ثانیه و خارج آن هر ۵ دقیقه تغییر می‌کند. عمر quote حداکثر ۶۰ ثانیه و محدود به تازگی feed است.
۳. در خرید، «موجودی کیف پول» انتخاب پیش‌فرض است. با ثبت خرید، ریال و طلا اتمیک جابه‌جا می‌شوند و پرداخت تازه‌ای لازم نیست.
۴. برای سناریوهای callback خرید، «درگاه ماک (خرید مستقیم)» را انتخاب کنید. مسیر قدیمی API نیز سازگار مانده است.
۵. «موفق بدون callback» با inquiry worker پیدا می‌شود. پرداخت دیررس خرید، پس از انقضای quote، به کیف پول ریالی می‌رود.
۶. برای سناریوی واقعی verify ناموفق، درخواست شارژ یا خرید مستقیم بسازید و «کسر وجه، verify ناموفق» را بزنید. در جزئیات، paid/rejected و پیام رفع مغایرت دیده می‌شود؛ موجودی افزایش نمی‌یابد. اجرای تطبیق، gateway_only گزارش می‌کند. «تأیید مجدد درگاه ماک» نتیجه را اصلاح می‌کند و worker همان پرداخت را یک بار نهایی می‌کند؛ سپس گزارش تطبیق تازه بدون آن مغایرت خواهد بود. این عملیات بازپرداخت بانکی نیست.
۷. برای فروش قیمت تازه بگیرید. برداشت از ریال قابل استفاده است؛ شبا checksum معتبر می‌خواهد و پیش‌فرض نمونهٔ آزمایشی است.
۸. از تاریخچه، events، entries، jobs و اطلاعات charge/verify را ببینید. قطعی providerها از پنل پشتیبانی قابل کنترل است؛ موجودی و تاریخچه در قطعی قیمت هم نمایش داده می‌شوند.

برای سناریوهای ۱۰۰ درخواست و فروش هم‌زمان از تست خودکار استفاده کنید. UI تک‌کاربره است و نمایش دستی این موارد جایگزین تست نیست.

## API خلاصه

- `POST /api/quotes` → قیمت هر گرم ریال، زمان انقضا
- `POST /api/orders` با `Idempotency-Key`؛ شارژ مستقل: `{kind:"topup",amount:"100000000"}`
- خرید از کیف پول: `{kind:"buy",amount:"10000000",quoteId:"...",fundingSource:"wallet"}`
- خرید مستقیم درگاه: همان خرید با `fundingSource:"gateway"`؛ حذف این فیلد برای سازگاری به معنی gateway است
- فروش: `{kind:"sell",gold:"10000",quoteId:"..."}`؛ gold به میکروگرم
- برداشت: `{kind:"withdraw",amount:"100000",sheba:"IR..."}`
- `POST /api/mock/payments/:id` با `{mode:"success"}`؛ modes: success/failure/duplicate/late/missing/failed_verify
- `POST /api/mock/payments/:id/resolve-verification` تأیید مجدد پرداخت شارژشده با verify ناموفق؛ فقط ماک، پردازش مالی async
- `POST /api/gateway/callback/:id` فقط اعلان است؛ مبلغ/نتیجه از verify خوانده می‌شود
- `GET /api/balances`، `GET /api/orders`، `GET /api/orders/:id`
- `POST /api/support/reconcile`، `GET /api/support`
- `POST /api/support/jobs/:id/retry` برای dead job

اعداد مالی در API رشتهٔ صحیح هستند. amount ریال است، نه تومان. کارمزد معامله ۱٪، شارژ بدون کارمزد و مبنای قیمت ۱۰۰ میلیون ریال/گرم با نوسان هر ۳۰ ثانیه، صرفاً فرض دمو است. سیاست انقضا بر اساس زمان پرداخت در ماک است، نه زمان callback.

## بررسی انجام‌شده در این مرحله

- TypeScript typecheck و ۴۹ تست خودکار موفق؛ شامل ۱۰۰ درخواست هم‌زمان، رقابت خرید از کیف پول و برداشت، شارژ مستقل، feed سی‌ثانیه‌ای، verify ردشده پس از کسر وجه، replay پیام RabbitMQ، DLQ و بازیابی.
- اجرای واقعی همهٔ سرویس‌ها با `docker compose up --build -d` موفق.
- smoke از HTTP: شارژ با callback تکراری → خرید از کیف پول → کسر وجه و verify ردشده → رفع مغایرت → فروش → برداشت → تطبیق بدون مغایرت؛ جمع ledger برای هر دو دارایی صفر.
- بررسی syntax فایل JS و تست مرورگری مسیر شارژ → کسر وجه با verify ناموفق → رفع مغایرت → خرید از کیف پول موفق؛ موجودی و پیام‌های وضعیت در رابط تأیید شدند. ویدیوی اجرای هفت سناریو در بستهٔ تحویل محلی آماده است.

برای تکرار smoke با ایجاد سفارش‌های ساختگی تازه و بدون پاک‌کردن داده‌ها:

```sh
node scripts/smoke.mjs
```

ارتقا از نسخهٔ قبلی با همان `docker compose up --build -d` انجام می‌شود؛ migration افزایشی است، حساب‌ها و سندهای قبلی حذف نمی‌شوند. درخواست‌های idempotent قدیمی همچنان پاسخ ذخیره‌شدهٔ خود را دریافت می‌کنند. حالت‌های آزمایشی failed_verify که در نسخهٔ قبلی ایجاد شده‌اند بازنویسی نمی‌شوند؛ برای رفتار جدید سفارش تازه بسازید.

## بخش پنجم — دمو و قرارداد API

- بازار: شنبه تا چهارشنبه، ۰۹:۰۰ تا ۱۵:۰۰ تهران. سقف خارج بازار برای خرید و فروش هر کدام ۵۰۰ میلیون ریال در روز محلی است.
- سفارش مازاد سقف کامل صف می‌شود؛ خرید به ریال و فروش به میکروگرم ثبت می‌شود. دارایی رزرو و تا قبل از اجرا قابل لغو است. قیمت اجرا اولین قیمت پس از بازشدن است؛ قیمت فعلی تضمین نمی‌شود.
- `GET /api/market`: ساعت و وضعیت بازار، نوبت بعد و سقف باقی‌مانده.
- `POST /api/orders/:id/cancel`: لغو صف و آزادسازی رزرو؛ تکرار امن است، سفارش اجراشده 409 می‌دهد.
- خرید مازاد سقف از کیف پول می‌تواند بدون quoteId ثبت شود؛ معاملهٔ فوری و فروش، quote معتبر و تازه می‌خواهند.
- `GET /api/balances` اکنون `reservedGoldUg` را نیز برمی‌گرداند؛ `rials` و `goldUg` فقط قابل استفاده‌اند.
- قیمت کهنه: بیشتر از ۶۰ ثانیه در بازار یا ۶ دقیقه بیرون بازار. نداشتن tick تا ۱۵ دقیقه قابل شبیه‌سازی است؛ انتظار صف بودجهٔ خطای retry را مصرف نمی‌کند.
- `POST /api/mock/market` با `{clock:"2026-11-17T20:00:00+03:30"}` ساعت دمو را ثابت می‌کند؛ `clock:null` ساعت واقعی را برمی‌گرداند. با `{pauseFeed:true}` وقفهٔ ۱۵ دقیقه‌ای آغاز و با false متوقف می‌شود. ساعت ماک مشترک API/worker است؛ retry و timeout زیرساخت از ساعت واقعی استفاده می‌کنند.
- worker صف را خودکار می‌گرداند؛ `POST /api/support/process-queue` فقط بررسی فوری scheduler را درخواست می‌کند.

برای نمایش سریع: شارژ کافی → ساعت آزمایشی ۲۰:۰۰ → خرید ۶۰۰ میلیون ریال از کیف پول → مشاهدهٔ رزرو و لغو، یا انتقال ساعت به نوبت `execute_after` برای اجرای خودکار. با ساعت ثابت ماک، ۳۰ ثانیه پس از execute_after را انتخاب کنید تا اولین tick نیز رسیده باشد. برای فروش صف‌شده، ابتدا در ساعات باز طلا بخرید. پس از دمو «بازگشت به ساعت واقعی» را بزنید.

```sh
node scripts/smoke-market.mjs
```

این smoke با سفارش‌های ساختگی، صف/لغو/بازشدن و رد قیمت کهنه را بررسی و در پایان ساعت اصلی را بازیابی می‌کند. فرض‌های سقف شامل کارمزد، نبود تقویم تعطیلات و قرارداد نخستین tick در [معماری](docs/ARCHITECTURE.md) و [CHANGES](CHANGES.md) توضیح داده شده‌اند.


## تکمیل عملیات و تحویل

نسخهٔ نهایی با **۶۱ تست موفق** و بررسی TypeScript تأیید شد. برچسب `v1` همچنان خط مبنای پیش از بخش پنجم است.

- پرداخت کسرشده با verify ناموفق: پشتیبانی می‌تواند بازپرداخت به بانک را درخواست کند؛ وجه در suspense نگه داشته می‌شود و تا دریافت رسید خارجی قابل خرج نیست. `POST /api/support/orders/:id/refund`.
- خزانه و بانک رسید مستقل و idempotent دارند. اختلال خزانه، رسید مفقود/مقدار اشتباه و اختلال بانک قابل شبیه‌سازی‌اند. گزارش تطبیق، مغایرت درگاه، بانک و خزانه را جدا نشان می‌دهد؛ مهلت پیش‌فرض ثبت رسید ۱۲۰ ثانیه است.
- تطبیق روزانه از ساعت ۰۲:۰۰ تهران با scheduler پایدار انجام می‌شود؛ اجرای دستی نیز در پشتیبانی موجود است.
- `GET /api/history?limit=25&cursor=...` تاریخچهٔ keyset با cursor و سقف ۱۰۰ آیتم دارد؛ رابط از صفحه‌بندی استفاده می‌کند.
- صفحهٔ `http://localhost:3000/demo.html` هر هفت سناریو را با API و worker واقعی اجرا می‌کند و ساعت و تنظیمات اولیه را برمی‌گرداند. داده‌های آزمایشی جدید باقی می‌مانند. اجرای ضبط‌شدهٔ نهایی هر هفت مورد را با موفقیت گذراند.
- [معماری و قراردادهای مالی](docs/ARCHITECTURE.md) شامل دفتر حساب‌ها، suspense، بازپرداخت و اصلاح، نمونهٔ گزارش تطبیق، طراحی صندوق/کارت و برنامهٔ ۱۲ هفته‌ای است. [راهنمای دفاع](docs/DEFENSE.md) شامل مسیر ارائه، پرسش‌ها و اولویت یک روز اضافه است.

این محیط تک‌کاربره و محلی است. احراز هویت، مجوزهای چندسطحی پشتیبانی، موجودی فیزیکی خزانه، اتصال بانکی و تسویهٔ تجمیعی واریزهای درگاه به بانک، راه‌اندازی تولیدی محسوب نمی‌شوند. صندوق و کارت طراحی شده‌اند و در این MVP مسیر اجرایی ندارند. اصلاح دستی با تأیید دو نفر نیز قرارداد طراحی است؛ API ویرایش موجودی وجود ندارد.
